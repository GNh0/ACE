# SQL 작성·정리

이 스킬은 메인 에이전트가 직접 따른다. 별도 에이전트에 넘기지 않는다.

## 시작 전에

1. [lessons.md](references/lessons.md)를 읽는다. 과거에 사용자가 교정한 실수 목록이다. 이번 작업에 해당하는 항목은 아래 규칙보다 우선한다.
2. 요청 종류를 정한다.

| 요청 | 할 일 | 볼 문서 |
| --- | --- | --- |
| 정렬·정리만 | 의미를 바꾸지 않고 서식만 고친다. 로직 규칙 위반은 고치지 말고 위치만 보고한다. | [style.md](references/style.md) |
| SELECT 작성·수정 | 결과 한 행의 단위, 포함·제외 조건, 표시용 JOIN과 필수 JOIN을 먼저 정한다. | [select.md](references/select.md), [style.md](references/style.md) |
| SP를 새로 만들기 | 인자 선언, XML 파싱, 헤더+상세 저장 골격을 그대로 따른다. | [procedure.md](references/procedure.md) |
| BOM 전개, 월별 피벗 등 복잡한 조회 | 결과 한 행의 단위를 먼저 적고, 파생마다 그 단위를 지키는지 확인한다. | [complex-select.md](references/complex-select.md) |
| 마감 검증, 채번, 키 분해 등 공통 함수 | 기존 공통 개체를 쓴다. 새로 만들지 않는다. | [kone.md](references/kone.md) |
| SAVE 작성·수정 | 호출 모드(WORKTYPE), 선택 키, XML 행 상태(NEW/MOD/DEL)를 호출부와 맞춘다. | [save.md](references/save.md), [style.md](references/style.md) |

3. 기존 SP를 고치면 **원본 전체**와 **실제 호출부(C# 또는 PB)**를 먼저 읽는다. 새 SP는 사용자에게 헤더에 쓸 작성자 이름과, 작성 방식을 참고할 기존 SP(같은 역할의 SELECT 또는 SAVE)를 확인하고 그 SP를 처음부터 끝까지 읽는다.

## 항상 지키는 규칙

- 리터럴·주석 밖의 SQL은 모두 대문자. 선행 쉼표.
- 원래 JOIN 종류·순서, 조건, 출력 열 순서, 리터럴, 한글, 주석을 보존한다.
- **잠금 힌트(UPDLOCK, HOLDLOCK 등)는 절대 쓰지 않는다.** 원본·참고 SP에 있어도 지운다. 사용자가 이번 작업에서 직접 요청한 경우만 예외.
- NULL·빈 값을 새로 대체하지 않는다. 산술식의 `ISNULL(..., 0)` 추가도 사용자 요청이 있어야 한다.
- WHERE 안의 EXISTS·IN 서브쿼리는 JOIN으로 바꾼다(수정·검토 요청일 때). 단 SAVE의 `IF EXISTS` 검증은 유지한다.
- SAVE에서는 건수 변수, MAX 순번 변수, 중간 결과 테이블 변수, WHILE·커서 행 단위 처리, NEW/EDIT 분기 복사를 쓰지 않는다. 자세한 형태는 [save.md](references/save.md).
- `@변수`는 문법상 꼭 필요한 것만 둔다.
- **SAVE SP 안에 트랜잭션 코드(BEGIN TRANSACTION, COMMIT, ROLLBACK, TRY/CATCH)를 쓰지 않는다.** C#의 `ExecSPTrn`이 맡는다. 검증 실패는 `RAISERROR … RETURN`만 한다.
- FROM·WHERE·ORDER BY는 SELECT와 같은 열에서 시작한다(왼쪽 맞춤). LEFT/RIGHT JOIN에는 `OUTER`를 쓴다. CTE는 꼭 필요할 때만 쓴다.
- LINQ·중간 테이블·빌드는 기본적으로 쓰지 않는다. 없으면 구현이 어렵거나 성능 차이가 극단적일 때만 쓰고 이유를 말한다.

## 작업 파일과 정리

- **소스 프로젝트 폴더에 작업용 파일을 만들지 않는다.** 비교용 사본, 초안, 추출물, 테스트 스크립트, 실행 결과, 로그는 시스템 임시 폴더(`%TEMP%`) 아래 작업별 폴더에 둔다.
- 소스 폴더에는 사용자가 요청한 최종 결과물만 쓴다. 파일 위치를 지정받으면 그 경로에만 쓴다.
- **SP·쿼리 `.sql` 파일은 솔루션 폴더 안에 만들지 않는다.** `.sln`이 있는 폴더의 **상위 폴더**에 `SQL\<YYYYMMDD>\` 폴더를 두고 거기에 쓴다(예: 솔루션이 `…\고객사\C_KONE120\`이면 `…\고객사\SQL\20261120\sp_XX000100_SAVE.sql`). SP는 DB에 적용하고 이 파일은 날짜별 기록으로 남긴다. 솔루션 안에 `SQL` 폴더가 이미 있어도 거기에 쓰지 않고, 사용자에게 알리고 상위로 옮기자고 제안한다. 이 폴더는 형상관리 대상이 아니므로 `.sql` 파일의 커밋을 할 일로 적지 않는다.
- 작업 중 띄운 빌드, 앱 실행, DB 연결, 백그라운드 터미널·프로세스는 끝나면 종료한다. 사용자가 띄운 것이나 다른 작업이 같이 쓰는 서비스는 건드리지 않는다.
- 끝내기 전에 소스 폴더에 내가 만든 임시 파일이 남았는지 확인하고(git 저장소면 `git status`), 남았으면 지운다. 출처를 모르는 파일은 지우지 말고 보고한다.
- 다음 작업에 계속 필요한 임시 파일은 남기되, 경로를 답변에 적는다.

## 끝내기 전에 (자체 점검)

작성이 끝나면 별도 검토 에이전트 없이 직접 아래를 확인하고 결과를 답변에 넣는다.

1. **원본 대조**: 기존 SP면 원본과 최종본을 나란히 비교해 요청하지 않은 변경이 없는지 본다.
2. **규칙 대조**: 위 규칙과 lessons.md 항목을 하나씩 대조한다. 위반이면 고친다.
3. **시나리오 표**: 바꾼 조회·저장 경로마다 채운다. 한쪽만 맞으면 완료가 아니다.

| 구분 | 확인할 사례 | 근거 |
| --- | --- | --- |
| 정상 | 포함·갱신되어야 할 행 | 실행 결과 / 정적 대조 / 미확인 |
| 왕복 | 조회한 그대로 수정 저장한 뒤 다시 조회해도 수량·금액·순번이 그대로인지(조회와 저장의 행 단위가 같은지) | 실행 결과 / 정적 대조 / 미확인 |
| 제외·경계 | 완료된 이전·현재 공정 행, EDIT에서 자기 문서의 기존 수량, 복합키 일부 불일치, 요청하지 않은 WORKTYPE 분기, NULL·빈 값·0, 여러 행·선택 없음 | 실행 결과 / 정적 대조 / 미확인 |

해당 없는 칸은 이유를 적고, 실행하지 못한 사례는 `미확인`으로 둔다. DB 실행은 사용자가 지정한 서버·DB 범위에서만 한다.

마지막으로 [작업 파일과 정리](#작업-파일과-정리)대로 임시 파일과 띄운 프로세스를 정리했는지 확인한다.

## 교정을 받으면 (Compound)

사용자가 결과를 교정하면 고친 뒤, 같은 실수가 다시 나오지 않도록 ACE 저장소의 `skills/sql/references/lessons.md`에 항목을 추가하자고 제안한다. 형식은 lessons.md 맨 위에 있다. 사용자가 동의하면 추가한다.
