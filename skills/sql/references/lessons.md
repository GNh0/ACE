# SQL 교정 기록

사용자가 교정한 실수와 그 뒤로 지킬 규칙이다. 작업 전에 읽고, 해당하면 다른 규칙보다 우선한다.

항목 형식:

```
## <짧은 제목> (YYYY-MM-DD)
- 실수: <무엇을 잘못했나>
- 규칙: <앞으로 어떻게 하나>
```

새 항목은 맨 아래에 추가한다. 더 이상 맞지 않는 항목은 지운다.

---

## 잠금 힌트 금지 (2026-11-20 이전부터 반복)
- 실수: SAVE에 `WITH (UPDLOCK, HOLDLOCK)`을 넣거나, 원본에 있던 것을 그대로 두었다.
- 규칙: 잠금 힌트는 쓰지 않는다. 원본·참고 SP에 있어도 지운다. 사용자가 이번 작업에서 직접 요청한 경우만 남긴다.

## 별칭은 업무 역할로 (KH 3.6.2)
- 실수: 별칭을 JOIN 순서나 테이블명 첫 글자로 정했다.
- 규칙: 같은 업무의 보조·상세 테이블은 기준 글자에 번호(A1, B1)를 붙이고, 새 업무만 다음 글자를 쓴다. [style.md](style.md#별칭-역할)

## 식별자 전부 대문자 (KH 3.6.3)
- 실수: 출력 열 이름(`AS` 뒤)이나 함수·프로시저 이름의 원래 대소문자를 남겼다.
- 규칙: 리터럴·주석·`[...]` 안만 빼고 모두 대문자.

## EXISTS/IN 서브쿼리 → JOIN (KH 3.6.4)
- 실수: WHERE의 EXISTS·IN 서브쿼리를 그대로 두었다.
- 규칙: 연결 키로 GROUP BY한 파생 테이블을 JOIN한다. [select.md](select.md#exists--join)

## SAVE 고정 규칙은 원본에 있어도 고친다 (KH 3.6.5)
- 실수: 원본에 건수 변수·여러 COMMIT·조기 RETURN이 있다는 이유로 유지했다.
- 규칙: SAVE 로직을 고칠 때는 [save.md 고정 규칙](save.md#save-고정-규칙)대로 바꾼다. 서식 정리만 맡았으면 바꾸지 않고 위치만 보고한다.

## @변수 최소화 (KH 3.6.6)
- 실수: 한 번 대입하고 한 번 읽는 변수, 헤더 값을 복사한 변수를 만들었다.
- 규칙: 그 자리에서 식을 쓰거나 테이블 변수·대상 행을 JOIN해 읽는다.

## 집합 기반 배분 (KH 3.6.7)
- 실수: WHILE·커서·`SELECT TOP 1 @변수`로 한 행씩 배분하고, NEW/EDIT 분기에 같은 코드를 복사했다.
- 규칙: 누적 구간 JOIN으로 INSERT 한 문장에 쓴다. 공통 처리는 한 번만 둔다. [save.md](save.md#배분-insert)

## INSERT 긴 값은 줄 끝으로 (KH 3.6.8)
- 실수: 30자 넘는 값이 줄 중간에 있어 다른 줄의 열을 수십 칸씩 띄웠다.
- 규칙: 긴 값은 그 줄의 마지막 항목으로 두고 다음 열은 다음 줄에서 시작한다. [style.md](style.md#insert-열-대응)

## SAVE SP에 트랜잭션 코드 금지 (2026-11-20)
- 실수: SAVE SP 안에 `BEGIN TRANSACTION`·`COMMIT`·`ROLLBACK`·`TRY/CATCH`나 `@STARTTRANCOUNT`를 넣었다.
- 규칙: C#의 `ExecSPTrn`이 시작·커밋·롤백을 맡으므로 SP에는 쓰지 않는다. 검증 실패는 `RAISERROR … RETURN`만 한다. [save.md](save.md#트랜잭션)

## 절은 왼쪽 맞춤 (2026-11-20)
- 실수: FROM·WHERE·AND를 SELECT 끝 글자에 맞춰 오른쪽으로 들여 썼다(`  FROM`, ` WHERE`, `   AND`).
- 규칙: FROM·WHERE·GROUP BY·ORDER BY는 SELECT와 같은 열에서 시작하고, AND는 두 칸 들인다. 기존 SP에 오른쪽 맞춤이 있어도 따라 하지 않는다.

## 공통코드 이름은 JOIN, 사용자 이름은 함수 (2026-11-20)
- 실수: 공통코드 이름까지 `F_BA011T_FIND_SUBNM` 함수로 가져오게 했다.
- 규칙: 공통코드 이름은 `BA011T`를 LEFT OUTER JOIN한다. 사용자 이름은 가장 바깥 SELECT에서만 `F_FIND_USERNM` 함수를 쓰고, 대량 집계·수십만 건 조회에서는 JOIN한다(실측: 58만 건에서 함수 1.1초, JOIN 0.08초). [kone.md](kone.md)

## 조회와 저장의 행 단위를 맞춘다 (2026-11-20, C_KONE120 MA100500)
- 실수: 저장은 여러 행을 `GROUP BY`로 합쳐 상세 1행으로 넣고, 상세 조회는 하위 테이블 행마다 1행씩 돌려주면서 합쳐진 금액을 그대로 붙였다. 다시 열어 수정 저장하면 금액이 행 수만큼 불어난다.
- 규칙: SAVE를 쓰거나 고칠 때 "저장이 쓰는 상세 한 행"과 "DETAIL 조회가 돌려주는 한 행"이 같은 단위인지 대조한다. 조회 → 그대로 수정 저장 → 다시 조회했을 때 수량·금액이 변하지 않아야 한다. 합칠 때 `MAX(단가)`처럼 행마다 다른 값을 하나만 남기는 집계가 있으면 단위가 틀린 것이다.

## 수정 저장은 행 상태로 나눠 처리한다 (2026-11-20, C_KONE120 MA100500)
- 실수: EDIT에서 상세를 전부 지우고 다시 넣어 등록자·등록일이 수정한 사람으로 바뀌고, 수정할 때마다 채번을 새로 했다.
- 규칙: 상세는 `GBN`으로 나눠 DEL은 삭제, **MOD만 UPDATE**, NEW만 INSERT한다. 안 바뀐 행(UNC)은 건드리지 않고 수정자도 찍지 않는다. 헤더에서 상세로 복사해 둔 값(일자·거래처·화폐·환율)이 있으면 수정자 없이 상세 전체에 따로 맞춘다. 기존 SP가 "전부 지우고 다시 넣기"여도 따라 하지 않는다. 형태는 [procedure.md](procedure.md)의 골격과 같다. 채번은 NEW 행이 있을 때만 한다. 두 테이블에 짝이 되는 행을 넣을 때는 같은 정렬 키(유일한지 먼저 검증)로 번호를 매긴다.
